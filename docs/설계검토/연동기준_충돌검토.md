## 1. 충돌 없는 항목 (정합 확인)

### 1-1. 처리 순서 5단계

새 문서의 ①발화 분석(LLM) → ②서버 후처리 → ③진행 판단(규칙 엔진) → ④유도 정보 구성 → ⑤캐릭터 응답은, 기존 오케스트레이션(`llm_analysis.md` §4)의 "분석 LLM → 서버 규칙 → 생성 LLM"을 **세분화한 것이지 뒤집은 것이 아니다.**

- 기존 "서버 규칙" 1블록 = 새 문서의 ②후처리 + ③진행 판단 + ④유도 정보 구성.
- ②서버 후처리(evidence 원문 검증·중복 정리·약한 탐지 보정)는 **신설**이지만, "판단=코드, LLM=분석·생성만" 원칙을 약화시키는 게 아니라 **강화**한다 — LLM 출력을 코드가 한 번 더 검증하는 게이트가 추가된 것. STT의 실패 게이트·후처리 교정과 같은 계열의 장치다.
- 기존 분석 프롬프트 규칙 "evidence는 아이 발화에서 그대로 인용한다"(`llm_analysis.md` §5)의 **서버 측 집행 수단**이 생긴 것이므로 설계 의도와 정확히 맞물린다.

### 1-2. CLOSING 시 캐릭터 LLM 미호출

새 문서의 "CLOSING에서는 캐릭터 모델을 다시 호출하지 않는다"는 이전 설계의 **canonical 결정과 완전히 일치**한다. 근거 문서 전수:

| 문서 | 서술 |
|---|---|
| `llm_context.md` | "CLOSING이면 character_closing 고정대사 재생" |
| `llm_analysis.md` §4 다이어그램 | "character_closing 고정 대사 mp3 재생 (사전 생성, 과금 0)" |
| `tts_context.md` | "고정 대사: story_scenes.character_opening / character_closing … 사전 생성 가능" |
| AI 모델 선정 보고서 (아동 안전 장치) | "대화 마무리 멘트는 사전에 확정한 고정 대사만 사용" |
| Decision Log 2026-08-05 (LLM) | "CLOSING이면 고정 대사 재생" |

즉 새 문서는 이전 설계와 충돌하는 게 아니라, **DB 구조 문서 내부의 모순(한쪽에만 있던 'LLM이 마무리 대사 생성' 서술)을 다수 설계와 같은 방향으로 해소**해 준다. → 상세는 §2-A.

### 1-3. 유도 방식

새 문서: "진행 엔진이 직접 질문 문장을 만들지 않고, 부족한 요소명 + remainingWorries를 캐릭터 모델에 넘겨 대사로 표현."

기존 책임 경계 원칙(`llm_analysis.md` §4)과 동일하다:

- "LLM ②는 서버가 넘겨준 부족 요소(최대 1~2개)만 유도한다" = 서버는 **무엇을** 유도할지 지정, 캐릭터 모델은 **어떻게** 말할지만 담당.
- `remainingWorries`(캐릭터가 아직 걱정하는 것)는 캐릭터 모델 **입력 항목의 추가**일 뿐, 판단 주체를 바꾸지 않는다. 오히려 "부족 요소명"이라는 메타 정보를 캐릭터 세계관 언어로 번역해 주는 장치라 페르소나 유지에 유리하다. (저장 위치는 §2-C 참고.)

### 1-4. STT 흐름 연계 — 조정 불필요

- 새 문서 파이프라인은 ①발화 분석부터 시작 = 입력은 **STT 확정 텍스트(`messages.text`)**. `stt_raw_text`(원문)/`text`(교정 확정) 분리 저장, 경량 LLM 후처리 교정이라는 기존 STT 파이프라인 출력과 정확히 접합된다.
- "STT 실패 시 메시지 미생성 = 분석 대상 아님" 원칙과도 정합: 메시지가 없으면 ①이 호출되지 않으므로 ③진행 판단의 턴 카운트·저정보 연속 판정에 영향을 주지 않는다. STT 실패 재시도 대사("다시 말해줄래?")는 분석 파이프라인 **밖**의 고정 응답이라 새 문서의 5단계와 부딪히지 않는다.
- 구분선이 명확히 유지됨: **STT 실패**(메시지 미생성, 카운트 제외) vs **UNCLEAR**(메시지 존재, `consecutive_low_information_turns` 카운트 포함). 새 문서도 utteranceValidity를 분석 출력으로 유지하므로 이 구분은 그대로 성립한다.

### 1-5. TTS 흐름 연계 — 조정 불필요

- ⑤캐릭터 응답(NORMAL/GUIDED 가변 대사) → 런타임 TTS, CLOSING → 사전 생성 오디오 재생. **"고정대사=사전 준비 오디오 / 가변질문=런타임 TTS"라는 TTS 아키텍처 결론과 그대로 일치**한다.
- 다시 듣기 요건은 `hash(캐릭터+텍스트)` 캐시(Decision Log TTS 항목)로 가변 대사까지 커버되므로 새 문서로 인한 변경 없음.

### 1-6. 표기 차이는 충돌 아님

`childIntent`/`child_intent`, `detectedElements`/`detected_elements` 등은 API 응답(camelCase) vs DB 컬럼(snake_case) 컨벤션 차이일 뿐이다. 문서에 "API/코드 camelCase ↔ DB snake_case 매핑" 한 줄만 명시하면 된다.

## 2. 충돌·불일치 항목 (결정 필요)

### 2-A. CLOSING 대사 생성 방식 — 3서술 혼재 → **고정 `character_closing` 재생으로 통일**

현재 문서군에 세 가지 서술이 공존한다:

1. ~~"서버가 CLOSING 확정 → 캐릭터 LLM이 마무리 대사 생성"~~ (DB 구조 문서 한쪽) — **유일한 이탈 서술. 폐기 대상.**
2. "고정 `character_closing`을 두고, CLOSING이면 서버가 조회해 재생" (DB 구조 문서 story_scenes/utterance_analyses 참고 노트 + 분석 문서 전부)
3. "장면 설정에 정의된 종료 처리 사용" (새 문서) — `character_closing`이 곧 장면 설정(story_scenes) 필드이므로 **2를 포괄하는 표현. 실질 동일.**

**권고: 2로 통일** (새 문서의 3은 2를 가리키는 것으로 해석·명문화). 근거:

- **아동 안전**: "마무리 멘트는 사전 확정 고정 대사만"이 보고서에 안전 장치로 명시됨 — LLM 생성 마무리는 이 장치를 스스로 무너뜨린다.
- **시연 안정성**: 세션의 마지막 인상을 결정하는 대사가 LLM 호출 실패·품질 편차에 노출되지 않는다. CLOSING은 LLM 장애 시에도 코드만으로 완결되는 폴백 경로가 된다.
- **비용·지연 0**: 사전 배치 생성 mp3 재생(과금 0, 즉시 재생) — 이미 TTS 아키텍처가 이 전제로 확정됨.
- **판단=코드 원칙**: 종료 시점에 LLM을 다시 끼우면 "종료를 LLM이 마무리한다"는 회색 지대가 생긴다.

**통일 문안 제안**: "서버 규칙이 CLOSING을 확정하면 캐릭터 LLM을 호출하지 않고, `story_scenes.character_closing`(사전 생성 오디오)을 조회해 재생한다."

→ 조치: DB 구조 문서에서 서술 1 삭제·수정. 새 문서의 "장면 설정에 정의된 종료 처리" 문구 뒤에 `character_closing` 필드명을 괄호로 명시해 해석 여지 제거.

> **[확정 · 2026-08-07]** 사용자 결정: **고정 `character_closing` 재생이 요구사항.** Notion 「DB 구조_260803_수정안」 원문 확인 결과 이탈 서술은 §5 story_scenes 참고 절의 한 줄뿐이며(같은 장의 컬럼 정의표와 §6·§7·§8은 모두 고정 재생), 해당 한 줄만 Notion에서 삭제하면 정리 완료. Supabase 실제 스키마는 이미 이 기준에 부합(character_closing 필수 컬럼 존재). 아울러 Notion 문서가 요구사항 SoT이므로 §2-C(element_criteria/element_worries)·§2-D(raw 병행 저장)의 스키마 추가 권고는 요구사항 개정 전까지 보류.

### 2-B. 분석 출력 필드 — `main_point` 유무 (4필드 vs 3필드) → **4필드 유지 권고**

실제 불일치다. 기존 스키마(`llm_analysis.md` §5)는 `child_intent / main_point / detected_elements / utterance_validity` 4필드를 **required**로 확정했고 structured output 스키마·`utterance_analyses` 저장까지 연결돼 있는데, 새 문서는 `childIntent / detectedElements / utteranceValidity` 3필드만 명시한다.

**권고: `main_point` 유지** (새 문서가 누락한 것으로 보고 추가 반영). 근거:

- 비용·지연 영향 없음: 출력 ~200토큰 예산 안의 한 문장. 제거해도 얻는 것이 사실상 없다.
- 이미 확정된 산출물 3곳(structured output 스키마·프롬프트·`utterance_analyses` 컬럼)과 연결돼 있어 제거 비용이 더 크다.
- 세션 리뷰·시연 후 분석에서 "아이가 무슨 말을 했는지"를 evidence 조각이 아닌 문장 단위로 남기는 유일한 필드다 (`child_intent`는 의도, `main_point`는 내용 요약으로 역할이 다름).

단, 반대로 **제거를 택한다면** 다음 3곳을 동시에 수정해야 정합이 유지된다: ① `llm_analysis.md` §5 JSON 스키마(required 목록 포함) ② 분석 프롬프트 ③ `utterance_analyses` 테이블 컬럼. 어느 쪽이든 "한쪽 문서만 고치는" 상태가 가장 나쁘다.

### 2-C. `elementCriteria` · `targetElements` 신설 — 원칙 긴장 1건 + 스키마 공백 2건

#### (1) 탐지 범위 원칙 — targetElements가 탐지를 제한하면 안 됨

기존 경계 원칙은 "분석 LLM은 '무엇이 부족한가'를 판단하지 않는다"였다. `targetElements`를 분석 입력에 넣는 것 자체는 판단 위임이 아니라 **문맥 제공**이므로 허용 가능하지만, 만약 **탐지를 targetElements로 한정**하는 의미라면 실질 충돌이 생긴다:

- `accumulated_elements`의 의미가 "발화에서 관찰된 요소"에서 "목표 중 관찰된 요소"로 바뀐다.
- **감정분석 요건 파손**: MVP 요건의 "감정 분석"은 EMOTION 요소 추출로 구현되는데, EMOTION이 target이 아닌 장면에서는 감정이 기록되지 않게 된다.

**권고 명문화**: "분석 LLM은 항상 8요소 전체(DECISION~REQUEST)를 탐지 대상으로 한다. `elementCriteria`/`targetElements`는 인정 기준(경계 사례 판정)과 주의 집중을 위한 참고 입력이며 탐지 범위를 제한하지 않는다." — 이 한 줄이 새 문서에 없으면 구현 단계에서 반드시 갈린다.

#### (2) `elementCriteria`의 저장 위치 — `story_scenes` 반영 필요

`elementCriteria`(장면별 요소 인정 기준)는 장면 저작 시 확정되는 콘텐츠 데이터로, `character_opening`/`character_closing`과 같은 계열이다. 현재 DB 구조에 대응 필드가 없다.

**권고**: `story_scenes.element_criteria` (JSON, 예: `{"REASON": "구체적 까닭이 한 가지 이상…", …}`) 추가. 장면 로드 시 분석 프롬프트의 가변부(유저 프롬프트)에 주입. 프롬프트 하드코딩이나 서버 설정 파일 분산은 "장면 콘텐츠는 story_scenes에 모인다"는 기존 구조를 깨므로 비권장.

#### (3) `remainingWorries`의 저장 위치 — 미정의

캐릭터 모델 입력으로 새로 등장했으나 저장 위치가 어느 문서에도 없다. 성격상 "장면 × 요소 → 캐릭터가 아직 걱정하는 것"의 저작 데이터이므로, `story_scenes`에 요소별 걱정 문구 필드(예: `element_worries` JSON)로 두는 것이 자연스럽다. ④유도 정보 구성 단계가 missing 요소명으로 이 테이블을 조회해 캐릭터 모델 프롬프트에 넣는 구조.

### 2-D. 서버 후처리 결과와 `utterance_analyses` 저장 — 관계 미정의

기존 흐름은 "분석 LLM → `utterance_analyses` 저장 → 서버 규칙"이었는데, 새 문서는 분석과 진행 판단 사이에 ②후처리(evidence 검증·중복 정리·약한 탐지 보정)를 끼운다. 그러면 **저장되는 것이 LLM 원본인지 후처리 확정본인지**가 미정이 된다 — 충돌이라기보다 새 문서가 만든 공백.

**권고**: STT의 `stt_raw_text`/`text` 분리와 같은 패턴 적용 — `utterance_analyses`에 **LLM 원본 JSON(raw)과 후처리 확정 요소를 병행 저장**하고, ③진행 판단(accumulated 갱신)은 확정본만 사용. 근거: "이상 발화 시 STT 오인식인지 분석 오류인지 단계별 분리 진단"이라는 기존 디버깅 원칙(llm_analysis.md 부록)이 분석↔후처리 사이에도 그대로 필요하다. 약한 탐지 보정이 과하게 깎았는지 원본으로 검증할 수 있어야 임계 튜닝이 가능하다.

## 4. 한 줄 결론

새 문서는 이전 설계와 **구조적으로 충돌하지 않는다** — 처리 순서·CLOSING 무호출·유도 방식·STT/TTS 접합 모두 기존 "판단=코드" 원칙의 세분화·강화다. 실제 손봐야 할 것은 4건: **CLOSING은 고정 `character_closing` 재생으로 통일**(DB 문서의 LLM 생성 서술만 폐기), **`main_point`는 유지**(새 문서에 추가), **elementCriteria/remainingWorries는 `story_scenes` 필드로 신설 + 탐지 범위(8요소 전체) 명문화**, **후처리 전후를 raw/확정으로 병행 저장**.
